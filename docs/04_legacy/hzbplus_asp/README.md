## 这个项目是什么

```
slope = LINEARREG_SLOPE(total_turnover, timeperiod = N)

slope 由负数转为非负  → 买入信号
slope 由正数转为负数  → 卖出信号
其他                 → 保持原仓位
```

`N`（`LONGPERIOD`）通过全市场逐股寻优得到，范围 5~120。

**执行**：`signal_lag = 1`（今天收盘算信号，**次日**开盘/收盘执行）。
这一点做得对 —— `hzbplus_README.md` 明确写了"为了避免使用当天成交额生成信号后又在当天成交"。

## 最值得学的三点

### 1. 日期定义写成了独立的一节（`HZBPlus_working_README.md` §1）

> **`trade_signal_history.csv` 中的日期是信号产生日期，不是成交日期。**

并且给了一张逐日的对照表，说明"CSV 哪一行 → RQAlpha 在哪天执行"。

**为什么这值得学**：信号日 / 成交日的错位，是回测与实盘不一致的第一大来源。
它把这个定义放在文档**第一节**，而不是埋在代码注释里。

本仓库对应位置：`docs/01_architecture/conventions.md` §2（标签命名）与
§3（时点近似必须标注）。

### 2. 两层加速的设计

```
第一层：按股票分批    全市场 → 多个 batch → 每个 batch 独立回测并输出 part 文件
第二层：对参数向量化  IndicatorFactory 一次性生成所有 period 的信号矩阵
                     → 一次性构建 vbt.Portfolio.from_signals
```

**结果矩阵**：

```
order_book_id,5,6,7,8,...,120
000001.XSHE,0.12,0.10,0.08,...,0.15
```

**关键**：它还输出了 `param_return_matrix`（每只股票每个 period 的收益），
理由写得很到位：**"适合后续分析参数稳定性，而不是只看最优值"**。

**这个自觉性很值得学**：只看最优值 = 只看 N 次搜索的最大值 = 最容易被 DSR 惩罚的用法。

### 3. 诚实地列出"注意事项"

> 1. `signal_lag=1`，避免未来函数
> 2. 参数寻优结果属于样本内最优，**容易过拟合**。后续建议拆分训练期和测试期。
> 3. 当前版本**没有精确模拟涨跌停、停牌无法成交**等微观交易约束。
> 4. 全市场长周期数据较大，建议从小 batch、小 workers 试跑，再逐步放大。

**这四条就是它的"已知局限"。** 写出来，并且指出了改进方向。

## 它缺的（也就是新仓库要补的）

这个项目在**工程层面**很完整（生产化、日志、MySQL、故障恢复），
但在**研究方法层面**几乎是空的：

| 缺什么 | 后果 |
|---|---|
| 没有截面 IC / 分层 | 不知道这个斜率信号是"个股 alpha"还是"市场 beta" |
| 没有组合层回测 | 单股寻优的结果无法组合成可执行的策略 |
| **每只股票一次参数寻优** | `N` ≈ 股票数 × 参数格数 ≈ 5000 × 116 ≈ **58 万次搜索** → DSR 接近 0 |
| 没有样本外 / 禁运 | "最优 period" 的分布本身就是过拟合的产物 |
| 没有涨跌停 / 停牌约束 | 回测不可执行 |

**建议的改造路径**（如果要把 ASP 升级为可验证的因子）：

```
1. 截面化：不再"逐股寻优"，改为"同一天横截面比较斜率"
   → N 从 ~58 万次降到 ~10 次（只测几个窗口）
2. 因子层：IC / 分层 / NW-t / 逐年
3. 组合层：选 top-N 持有一段时间
4. 审计：DSR / 前视 / 脆弱性
```

**注意**：截面化之后，"斜率"的含义会变 ——
从"这只股票的成交额趋势在变强"变成"相对其他股票，它的成交额趋势更强"。
**这是两个不同的假设，需要重写 `idea.md`。**
