# 0001 · 采用五层结构（data / library / research / decision / knowledge）

- **状态**：已接受
- **日期**：2026-11-20
- **关联**：[`../01_architecture/repo_layout.md`](../01_architecture/repo_layout.md)

## 背景

旧项目 `wpqc` 有 3 年积累、约 40 个 Python 文件、70+ 个 CSV/PKL 在根目录、
5 份长篇文档（合计 100 KB）。**信息是全的，但找不回来**：

- 想知道"这个数字从哪来"→ 要在 5 个 md 和 20 个 CSV 之间跳
- 想知道"这个文件是什么"→ 靠文件名记忆（`LDmac_cpv_016.csv`）
- 想知道"上次为什么放弃这条路"→ 没有记录

根本原因不是"没整理"，是**没有层级**，所以无法判断任何东西的角色。

## 选项

**A. 单一目录 + 前缀命名**（旧项目的做法）

```
wpqc/
├── data_*.parquet
├── feat_*.py
├── res_*.csv
└── doc_*.md
```

- 优点：迁移成本最低
- 缺点：层级信息编码在文件名里，靠约定维持，一旦有人破例就崩；无法自动化校验

**B. 按项目分目录，每个项目内部自洽**

```
projects/wpqc/{src,data,docs}
projects/hzbplus/{src,data,docs}
```

- 优点：项目间隔离清晰
- 缺点：**知识无法跨项目复用** —— 而跨项目复用恰恰是最有价值的（PIT 教训、审计方法）

**C. 按"角色的稳定性"分五层**（本决定）

```
data（可重建，会变）
  → src/factorlab（被复用两次以上才进这里）
    → research/<direction>（一次研究的全部痕迹）
      → registry（当前状态，每轮更新）
        → docs/03_knowledge（结论，长期稳定）
```

- 优点：每一层有唯一职责；**判据清晰**（"这段代码会被第二个研究用吗？"→ 决定放哪）
- 缺点：稍微啰嗦，一次研究要碰 3~4 个目录

## 决定

**采用 C（五层结构）。**

判据：

| 情况 | 放哪 |
|---|---|
| 只有这一个研究方向会用 | `research/<dir>/` 里就地放着 |
| 第二个研究要用它了 | 搬进 `src/factorlab/` |
| 是配置不是逻辑 | `configs/` |
| 是结论不是代码 | `docs/03_knowledge/` |

## 代价

1. **一次研究要碰多个目录**（data → research → registry → docs）。比"一个目录写完"啰嗦。
2. **"要不要进 src/"的判据需要判断力**。"会被复用两次"在事前很难判断。
   实践上允许**先复制，第二次用时再搬** —— 但搬的时候要在原处留一行 import。
3. **对单人项目的收益小于团队**。如果只有一个人做，全部放一个目录也能活。
   但旧项目的教训是：**18 个月后一个人也会看不懂自己写的东西。**

## 什么时候应该重新考虑

- 如果 `src/factorlab/` 超过 30 个模块，说明"复用"变成了"框架"，应该按领域拆子包
- 如果 `research/` 目录数超过 50 且大部分已完结，应该加 `research/_archive/`
- 如果出现多个并行研究者，`registry/` 的并发写入会成为问题 → 那时才考虑数据库（见 ADR 0003）

## 影响

- 所有路径引用以本结构为准
- `docs/01_architecture/repo_layout.md` 是本文的展开
- `research/_template/` 是这一结构的实例化
