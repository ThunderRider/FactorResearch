# 06 · 架构决策记录（ADR）

> **记录"为什么这样设计"。** 代码和结构告诉你"是什么"，
> ADR 告诉你"当时有哪些选项、为什么选了这个、付出了什么代价"。

---

## 为什么需要 ADR

结构是团队共识的载体。**静默改动会让历史文档全部失效。**

一个真实场景：

> 三个月后有人想把 `data/features/` 改成宽表，因为"更快"。
> 他看了看代码，看不出为什么当初用了长表 —— 于是改了。
> 结果所有 `docs/03_knowledge/` 里引用的 `factor` 列名全部失效，
> 而没人知道他改了。

ADR 就是防止这件事的东西。

---

## 格式（很短，一页）

```markdown
# NNNN · <决定的一句话>

- 状态：提议 / 已接受 / 已废弃 / 已替代（被 NNNN 替代）
- 日期：YYYY-MM-DD
- 关联：链接到受影响的文档

## 背景
当时面对什么问题？有什么约束？

## 选项
A. ……  优点 / 缺点
B. ……  优点 / 缺点
C. ……  优点 / 缺点

## 决定
选了哪个，一句话。

## 代价
这个决定的代价是什么？什么情况下应该重新考虑？

## 影响
哪些文件/文档/流程因此确定下来。
```

**"代价"是最重要的一节。** 没有代价的决定，说明你没想清楚权衡。

---

## 什么时候写

| 写 | 不写 |
|---|---|
| 改变目录结构 | 重命名变量 |
| 改变数据格式（宽表 ↔ 长表） | 换库版本 |
| 改变口径（成本、标签、复权） | 修 bug |
| 引入新工具/外部依赖 | 加一个函数 |
| 改变流程（门禁、状态机） | 调整注释 |

## 编号规则

- 四位数字，从 0001 开始，只增不减
- 文件名 `<NNNN>-<kebab-case>.md`
- 被替代的 ADR **不删除**，状态改为「已替代（被 NNNN 替代）」
